# Задание 1. Анализ и планирование

## 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо включать и выключать отопление в своём доме через веб-интерфейс.
- Пользователи могут задать режим работы отопительного контура.
- Система хранит справочник установленного оборудования (таблица `sensors`) и его последнее известное состояние.
- Все команды идут в одном направлении: сервер → реле. Устройство само ничего не инициирует.

**Мониторинг температуры:**

- Система получает данные о температуре с датчиков, установленных в домах.
- Данные читаются **по запросу**: при обращении пользователя сервер синхронно опрашивает внешний сервис датчика (`GET /temperature?location=` и `GET /temperature/{sensorId}`).
- Пользователи могут просматривать текущую температуру в своих домах через веб-интерфейс.
- История измерений не сохраняется — в БД лежит только последнее значение.

**Что пользователь сделать НЕ может:**

- Самостоятельно подключить датчик — требуется выезд инженера.
- Управлять чем-либо, кроме отопления.
- Настроить автоматические сценарии.

## 2. Анализ архитектуры монолитного приложения

| Характеристика | Текущее состояние |
|---|---|
| Язык программирования | Go 1.22 |
| Веб-фреймворк | Gin |
| База данных | PostgreSQL 16, драйвер `pgx/v5` |
| Архитектура | Монолит: `handlers` → `db` в одном процессе и одном развёртывании |
| Схема данных | Одна таблица `sensors` (id, name, type, location, value, unit, status, last_updated, created_at) |
| Взаимодействие с устройствами | Синхронный HTTP, инициатор всегда сервер |
| Взаимодействие внутри приложения | Прямые вызовы функций, транзакционная целостность в одной БД |
| Асинхронность | Отсутствует: нет очередей, событий, подписок |
| Масштабируемость | Только целиком: нельзя отдельно масштабировать чтение телеметрии |
| Развёртывание | Требует остановки всего приложения |
| Наблюдаемость | Логи в stdout, health-check `GET /health` |
| Масштаб эксплуатации | ~100 веб-клиентов, ~100 модулей управления отоплением |

Структура кода монолита:

```
apps/smart_home/
├── main.go                        точка входа, роутинг, graceful shutdown
├── handlers/sensors.go            HTTP-обработчики CRUD датчиков
├── services/temperature_service.go синхронный клиент к temperature-api
├── db/db.go                       SQL-запросы напрямую из обработчиков
└── models/sensor.go               модель Sensor
```

**Существенная деталь.** В `GetSensors` монолит для **каждого** температурного
датчика делает отдельный синхронный HTTP-вызов к внешнему сервису
(`handlers/sensors.go:53-67`). Это классический N+1: время ответа списка
линейно растёт с числом датчиков, а недоступность `temperature-api` напрямую
деградирует основной пользовательский сценарий.

## 3. Определение доменов и границы контекстов

Выделены следующие домены. Для каждого указано, существует ли он в As-Is.

| Домен (bounded context) | As-Is | To-Be | Ответственность | Владеет данными |
|---|:---:|:---:|---|---|
| **Пользователи и дома** (Identity & Access) | частично | ✅ | Учётные записи, дома, права доступа к дому | `users`, `houses`, `house_members` |
| **Управление устройствами** (Device Management) | ❌ | ✅ | Каталог типов устройств, реестр экземпляров, доставка команд | `device_types`, `devices`, `device_commands` |
| **Управление отоплением** (Heating) | ✅ | ✅ | Зоны отопления, целевая температура, режимы | `heating_zones` |
| **Управление освещением** (Lighting) | ❌ | ✅ | Светильники, включение/выключение, яркость | `light_fixtures` |
| **Управление воротами** (Access / Gates) | ❌ | ✅ | Открытие, закрытие, блокировка, переходные состояния | `gates` |
| **Видеонаблюдение** (Monitoring) | ❌ | ✅ | Камеры, доступ к потоку, запись | `cameras` |
| **Телеметрия** (Telemetry) | ✅ (вырожденно) | ✅ | Приём, хранение и выдача измерений, контроль порогов | `telemetry_points`, `threshold_rules` |
| **Сценарии автоматизации** (Scenarios) | ❌ | ✅ | Пользовательские правила «условие → действия» | `scenarios` |
| **Уведомления** (Notifications) | ❌ | ✅ | Доставка и журнал уведомлений | `notifications` |

**Границы проведены по владению данными и по темпу изменений.**

Ключевое решение — отделить **«Управление устройствами»** от доменов
управления (отопление, свет, ворота, наблюдение). Реестр устройств меняется
при подключении партнёрского оборудования, а логика отопления — при изменении
бизнес-правил; это разные причины для изменения, поэтому разные сервисы.

**Как поддерживаются ещё неизвестные датчики.** Устройство описывается
записью справочника `DeviceType` с набором **возможностей** (`capabilities`):
`heating.setpoint`, `lighting.brightness`, `gate.open`, `telemetry.temperature`
и т. д. Команда адресуется возможности, а не модели прибора —
`(capability, action, payload)`. Поэтому:

- новый прибор партнёра подключается **созданием записи `DeviceType`** через
  `POST /api/v1/device-types`, без выката новых версий сервисов;
- доменные сервисы подписаны на `DeviceRegistered` и **сами решают**, интересно
  ли им устройство (по `category` или по наличию нужной `capability`);
  незнакомые категории просто игнорируются;
- транспорт команд и телеметрии не зависит от того, какие типы устройств
  существуют в системе.

## 4. Проблемы монолитного решения

1. **Синхронная связанность с устройствами.** Всё взаимодействие идёт
   «сервер → датчик» по запросу. Устройство не может само сообщить об
   изменении, поэтому невозможны ни реакция в реальном времени, ни
   автоматическое поддержание температуры.

2. **N+1 обращений к внешнему сервису.** Чтение списка датчиков порождает по
   HTTP-вызову на датчик. При росте со 100 до тысяч домов время ответа и
   нагрузка растут линейно, а отказ `temperature-api` роняет основной сценарий.

3. **Невозможность самообслуживания.** Каждое подключение требует выезда
   инженера. Это прямо противоречит цели «экосистема доступна пользователю в
   режиме самообслуживания по модели SaaS» и не масштабируется на несколько
   регионов.

4. **Жёстко зашита единственная предметная область.** Модель `Sensor` с полем
   `type` описывает только датчики. Добавление света, ворот и камер требует
   переписывания модели данных и обработчиков — расширение системы
   невозможно без изменения ядра.

5. **Нельзя масштабировать по частям.** Приём телеметрии (много записей, растёт
   быстрее всего) и управление устройствами (мало запросов) живут в одном
   процессе и масштабируются только вместе.

6. **Развёртывание с простоем.** Любое изменение требует остановки всего
   приложения. При 5 разработчиках, работающих над разными доменами, это
   создаёт очередь релизов и общий риск.

7. **Отсутствие истории телеметрии.** В БД хранится только последнее значение
   (`sensors.value`). Аналитика, графики и правила «если температура ниже X»
   принципиально невозможны.

8. **Общая точка отказа и общая схема данных.** Единая БД без изоляции:
   ошибка в одном сценарии способна повлиять на все остальные, а изменение
   схемы затрагивает всё приложение.

9. **Нет модели прав на дом.** Владение и доступ к дому не выражены в схеме —
   при переходе к SaaS с несколькими жильцами это придётся вводить с нуля.

# Задание 2. Проектирование микросервисной архитектуры

## Диаграмма контейнеров (Containers)

[`docs/c4/03-containers-to-be.puml`](docs/c4/03-containers-to-be.puml)

Состав целевой системы: API Gateway (YARP) + 9 микросервисов + RabbitMQ +
PostgreSQL (база на сервис) + имитатор партнёрского датчика температуры.

**Внутреннее устройство каждого микросервиса — чистая архитектура.**
Каждый сервис — один проект; слои разложены по папкам внутри него.
Направление зависимостей — `Api -> Infrastructure -> Application -> Domain`.
Для системы такого размера отдельный проект на слой оказался лишней
церемонией, поэтому граница слоёв держится соглашением, а не компилятором:

| Слой | Папка | Содержимое |
|---|---|---|
| Domain | `Domain/` | Сущности, агрегаты, value-объекты, доменные события, бизнес-правила, порты хранения. Не зависит ни от чего, кроме общих примитивов. |
| Application | `Application/` | Сценарии использования (по файлу на сценарий), DTO, исходящие порты. Не знает про EF Core и брокер. |
| Infrastructure | `Infrastructure/` | DbContext, конфигурации EF, репозитории, потребители RabbitMQ, адаптеры внешних систем. Реализует порты внутренних слоёв. |
| Presentation | `Api/` + `Program.cs` | Модули эндпойнтов и composition root. Только привязка HTTP к сценариям использования. |

Состояние As-Is оставлено в анализе как исходная точка: кода монолита в
решении нет, экосистема построена целиком заново на микросервисах.

## Принципы взаимодействия

**Между микросервисами — асинхронно, через события (RabbitMQ).**
Издатель не знает подписчиков; добавление потребителя не требует изменений в
издателе. Полный список контрактов —
[`docs/api/warmhouse-events.asyncapi.yaml`](docs/api/warmhouse-events.asyncapi.yaml).

**Между клиентом и системой — синхронно (REST через API Gateway),**
потому что пользователь ждёт немедленного ответа.

**С базой данных — database per service.** Каждый сервис владеет своей БД и
не обращается к чужим таблицам. Физически это один инстанс PostgreSQL — сознательное
упрощение MVP; логически базы независимы, и разнести их можно без изменения кода.
Связи между данными разных сервисов — логические, целостность обеспечивается
событиями (eventual consistency), а не внешними ключами.

**Проекции вместо распределённых запросов.** Доменные сервисы держат
локальную копию нужных им полей устройства (`heating_zones.device_id` и т. п.),
которая наполняется из `DeviceRegistered`. Это исключает синхронные вызовы
между сервисами на горячем пути.

[`docs/er/er-diagram.puml`](docs/er/er-diagram.puml)

**Ключевые сущности и связи:**

| Связь | Тип | Пояснение |
|---|---|---|
| Пользователь — Дом (владение) | 1:N | Каждый дом связан ровно с одним владельцем |

| Устройство — Команда | 1:N | История команд устройства |

| Пользователь — Уведомление | 1:N | Журнал доставки |

# Задание 4. Создание и документирование API

## 1. Тип API

Используются **оба** типа — по характеру взаимодействия:

**REST (OpenAPI 3.1)** — для синхронного взаимодействия «клиент → система»
через API Gateway. Пользователь, нажимая «открыть ворота» или запрашивая
список устройств, ждёт немедленного ответа с кодом результата. REST здесь
уместен: операции адресуются ресурсам, кэширование и коды состояния
работают штатно, а инструменты (Swagger UI / Scalar, Postman) доступны
всем командам, включая QA и поддержку.

**AsyncAPI 3.0 (RabbitMQ / AMQP)** — для взаимодействия «микросервис →
микросервис». Выбор асинхронного обмена обоснован тремя причинами:

1. **Телеметрия — это поток.** Устройства присылают измерения постоянно и
   независимо; издателю незачем ждать, пока их обработают. Синхронный вызов
   здесь превратился бы в тот же N+1, что и в монолите.
2. **У одного события несколько потребителей.** `TelemetryReported`
   обрабатывают и телеметрия (хранение, пороги), и отопление
   (авторегулирование). Издатель не должен знать их список.
3. **Изоляция отказов.** Недоступность сервиса уведомлений не должна мешать
   включить отопление. Брокер с повторами и error-очередью даёт это «бесплатно».

Дополнительно REST используется для приёма телеметрии от устройств, которые
не умеют работать с брокером (`POST /api/v1/telemetry`) — внутри такой запрос
всё равно превращается в событие, поэтому путь обработки един.

## 3. Ключевые эндпойнты микросервиса «Управление устройствами»

### Пример: отправка команды устройству

**Запрос**

```http
POST /api/v1/devices/01a05e08-0a92-7efa-826d-28a41f3c76e7/commands
Content-Type: application/json

{
  "capability": "heating.setpoint",
  "action": "set",
  "payload": { "target": "21.0" },
  "requested_by": "01a05e08-0718-7893-96dd-4e579251da3b"
}
```

**Ответ `202 Accepted`**

```json
{
  "id": "01a05e09-1111-7000-8000-000000000002",
  "device_id": "01a05e08-0a92-7efa-826d-28a41f3c76e7",
  "capability": "heating.setpoint",
  "action": "set",
  "payload": { "target": "21.0" },
  "status": "pending",
  "correlation_id": "01a05e09-1111-7000-8000-000000000003",
  "requested_at": "2026-09-01T17:34:46.000+00:00"
}
```

Код `202`, а не `200`: доставка команды устройству асинхронна, результат
запрашивается отдельно по `correlation_id` или `commandId`.

**Ответ `422 Unprocessable Entity`** — устройство не поддерживает возможность:

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.21",
  "title": "Возможность не поддерживается",
  "detail": "Устройство не поддерживает 'gate.open'. Доступно: heating.setpoint, heating.mode, telemetry.temperature.",
  "status": 422,
  "instance": "/api/v1/devices/01a05e08-.../commands",
  "trace_id": "0HNO89S9NIJCD:00000002",
  "service": "Управление устройствами"
}
```

Ошибки во всех новых сервисах возвращаются в формате **RFC 9457 Problem
Details** с добавленными полями `trace_id` и `service` — по ним поддержка
находит запрос в логах. Legacy-сервис сохраняет исторический формат
`{"error": "..."}`, чтобы не сломать существующих клиентов.

| Код | Когда возвращается |
|---|---|
| `200` | Успешное чтение или изменение |
| `201` | Ресурс создан |
| `202` | Запрос принят, обработка асинхронная |
| `204` | Успех без тела ответа |
| `400` | Некорректное тело запроса |
| `401` | Неверные учётные данные |
| `404` | Ресурс не найден |
| `409` | Конфликт (дубликат серийного номера, ворота заблокированы) |
| `422` | Запрос синтаксически верен, но недопустим по бизнес-правилам |
| `500` | Внутренняя ошибка |
| `503` | Зависимость недоступна (камера офлайн) |

# Задание 5. Работа с docker и docker-compose

## Что сделано

1. **`temperature-api`** — реализован на ASP.NET Core (.NET 10),
   [`src/Simulators/WarmHouse.TemperatureApi/`](src/Simulators/WarmHouse.TemperatureApi/).
   При запросе `/temperature?location=` отдаёт случайное значение температуры;
   соответствие «комната ↔ sensorId» (1 — Living Room, 2 — Bedroom,
   3 — Kitchen) реализовано в обе стороны, как в задании. Слушает порт **8081**.

   В целевой архитектуре этот сервис играет роль **имитатора партнёрского
   датчика**: он изображает прибор, доступный по HTTP, показания которого
   попадают в экосистему через приём телеметрии.

2. **Упаковка в Docker.** Общий многостадийный
   [`deploy/Dockerfile`](deploy/Dockerfile) (SDK → publish → `aspnet` runtime,
   запуск от непривилегированного пользователя `$APP_UID`) параметризован через
   `PROJECT_PATH` / `ASSEMBLY_NAME` / `APP_PORT`, поэтому один файл собирает
   все 11 образов.

   > В runtime-образ доустанавливается `libgssapi-krb5-2`: клиент RabbitMQ
   > обращается к GSSAPI при открытии соединения, а в slim-образе этой
   > библиотеки нет — без неё подключение к брокеру падает с ошибкой
   > `libgssapi_krb5.so.2: cannot open shared object file`.

3. **PostgreSQL в docker-compose** с healthcheck и скриптом инициализации
   [`deploy/postgres/init/01-databases.sql`](deploy/postgres/init/01-databases.sql),
   который создаёт по базе на каждый микросервис.

   > **Замечание по исходному `init.sql` из шаблона.** Тот скрипт начинается с
   > `CREATE DATABASE smarthome;` и `\c smarthome;`. Скрипты из
   > `/docker-entrypoint-initdb.d` выполняются уже **внутри** базы, созданной
   > по `POSTGRES_DB`, поэтому `CREATE DATABASE` завершился бы ошибкой
   > «database already exists», а `\c` — это команда psql, а не SQL. В нашей
   > схеме создание баз вынесено в отдельный скрипт, а таблицы каждого сервиса
   > создаёт он сам при старте.

4. **Схема данных каждого сервиса** создаётся на старте
   (`SchemaInitializer<TContext>` в общей инфраструктуре): сервис дожидается
   готовности PostgreSQL и применяет свою схему. Для учебного MVP используется
   `EnsureCreated`; в продуктивной системе на этом месте были бы миграции
   EF Core, применяемые отдельным шагом пайплайна.

## Состав docker-compose

| Контейнер | Порт | Роль |
|---|---|---|
| `postgres` | 5432 | Одна СУБД, по базе на сервис |
| `rabbitmq` | 5672 / 15672 | Шина событий и веб-консоль |
| `temperature-api` | 8081 | Имитатор датчика температуры |
| `gateway` | 8000 | Единая точка входа (YARP) |
| `identity`, `devices`, `heating`, `lighting`, `gates`, `monitoring`, `telemetry`, `scenarios`, `notifications` | 8010–8085 | Микросервисы экосистемы |

## Проверка

```bash
cd warmhouse-dotnet
docker compose up -d --build
bash deploy/smoke-test.sh
```

Скрипт [`deploy/smoke-test.sh`](deploy/smoke-test.sh) проходит через шлюз весь
целевой сценарий и проверяет, что событийная связка действительно работает:

1. регистрация пользователя и выпуск токена;
2. создание дома;
3. чтение каталога типов устройств;
4. самостоятельное подключение термостата;
5. **зона отопления создаётся сервисом `heating` автоматически** — по событию
   `DeviceRegistered`, без единого синхронного вызова между сервисами;
6. создание правила контроля порога и сценария автоматизации;
7. отправка измерения 15,5 °C;
8. измерение сохранено сервисом телеметрии, порог нарушен, сценарий выполнен и
   уведомление доставлено.

Имитатор датчика проверяется напрямую:

```bash
curl "http://localhost:8081/temperature?location=Living%20Room"
curl "http://localhost:8081/temperature/2"
```

При каждом вызове значение температуры разное.
